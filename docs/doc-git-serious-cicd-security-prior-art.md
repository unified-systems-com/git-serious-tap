# CI/CD security and software-supply-chain prior art — come-up-to-speed research for git-serious

**Date:** 2026-08-26. **Purpose:** model the industry, environment and operations that git-serious ("Visualize, track, and secure your CI/CD system — for humans and agents") will exist in, well enough to regulate the product's design. **Method:** ~200 web searches and ~250 page fetches across three parallel research streams (commercial products; open source; incidents) plus a direct pass on canonical guidance and the GitHub API surface; see §7. **Status of claims:** every load-bearing claim carries a URL; items not verified from a primary source are marked **[partially verified]** or **[unverified]**. Nothing in the repository was modified.

## Executive summary

1. **The observable that matters most is a conjunction, not a setting.** Across 35 incidents (2019–2026-05) the deadly pattern is *mutable action ref × privileged trigger (`pull_request_target`/`workflow_run`/`issue_comment`) × long-lived secret* — TanStack (2026-05), Trivy/LiteLLM (2026-03), Nx (2025-08), tj-actions (2025-03) and Ultralytics (2024-12) are each chains of 2–3 individually-tolerable preconditions. Linters report them separately; a graph reports the conjunction.
2. **The signal has moved from static state to change.** Five of the six most recent incidents were detectable from a *delta* — every tag of an action moving in one burst, a self-hosted runner appearing on a repo that never had one, a workflow authored by a first-time committer, a secret rotated while an old token stayed valid. No product or OSS tool found tracks a GitHub org over time; Scorecard's weekly BigQuery cron (public repos only) is the sole longitudinal dataset.
3. **Direct graph prior art exists and is fresh**: SpecterOps' BloodHound GitHub OpenGraph extension (2025-07; 27 node kinds, 152 edge kinds, computed `GH_CanPwnRequest`/`GH_CanWriteBranch`/`GH_CanAssumeIdentity`, read-only collector) and CNCF Cartography's GitHub module. Both are snapshots bound to Neo4j/BloodHound UI. Study their schemas before designing ours.
4. **Workflow static analysis is a commodity — consume it.** zizmor (41 audits, ~650 adopters, MIT), poutine (org crawl + inventory, Apache-2.0), CodeQL's Actions pack (26 queries, on by default), Scorecard (18 checks, public API + BigQuery). Re-implementing any of these would be waste; ingesting their findings as typed edges on the grid is the play.
5. **GitHub is absorbing enforcement, not legibility.** 2025–26 shipped SHA-pinning policy, immutable releases, checkout-v7 refusing fork code under `pull_request_target` (enforced 2026-07-20), workflow-execution rulesets with Evaluate mode, rule insights, an Actions Data Stream and a roadmap egress firewall. None of it is an org-wide inventory with relationships and history — that lane stays open, and GitHub's new rule insights / Data Stream are inputs to it.
6. **No commercial vendor found models rulesets or environments as objects**, and none joins rulesets + environments + OIDC subject claims + fine-grained PATs + App installations + runner groups + workflow pins in one read-only graph. Wiz (now Google) is closest on paper; the NHI vendors that modelled Apps/PATs best (Astrix, Entro, Oasis) were all acquired in summer 2026.
7. **"Read-only credential" needs to mean a GitHub App, not a PAT.** Fine-grained PATs inherit the user's role, so org-level Administration:read only works for an owner's PAT; the fine-grained-PAT inventory endpoints are GitHub-App-only; OAuth apps have no API at all; ruleset `bypass_actors` are returned only to callers with write access to the ruleset; the audit-log API is Enterprise-Cloud-only. Each is a design fact to confront early (§3.9).
8. **OWASP CICD-SEC-10's first recommendation is literally "Mapping the environment"**, and CICD-SEC-2/-8 demand continuous identity and third-party mapping with *granted vs used* permissions — the read-only graph is the standards-sanctioned starting point, not a novelty to defend.
9. **SLSA v1.2's new Source track (Nov 2025) is a ruleset-posture model with a continuity requirement** ("since which revision has this control been continuously enforced") — exactly the history question a graph answers and a scanner cannot.
10. **The 2026 threat is autonomous.** hackerbot-claw (Feb–Mar 2026, "powered by claude-opus-4-5") and prt-scan (Mar–Apr 2026, 500+ PRs) mass-probe weak `pull_request_target` workflows; TeamPCP chained Trivy → LiteLLM → Checkmarx → Bitwarden CLI with residual access surviving rotation. The defender's loop must be at least as automated — the Player-3 posture is table stakes, not a stretch goal.
11. **Genuine differentiators**: change-over-time on org state; conjunction findings across object types; App-based read-only posture that shows its own permissions in the inventory; agent-operable review surfaces (gato-x already ships an MCP server — the attacker tooling is ahead of the defender tooling here). **Table stakes**: per-workflow lint findings, pin drift, SHA-pinning status, branch-protection tiers.
12. **Open questions that must be settled empirically on our own org before spec** (§5): whether an App with Administration:read sees `bypass_actors`; whether rule-suite history exposes bypass events to a read-only App; what a Team-plan org can and cannot observe without the audit log; how far run logs can substitute for runner telemetry.

## 1. Products operating in this space (commercial)

Skeptical reading rule applied throughout: a capability counts only if a docs page, pricing page, or dated changelog says it; marketing-page claims are marked as such. Market context first, then per-product.

### 1.0 Market context as of 2026-08-26

- **GitHub itself is the biggest mover.** SHA-pinning + blocklist policy (2025-08-15), immutable releases GA (2025-10-28), Dependabot default 3-day cooldown (2026-07-14), **workflow execution protections** on the ruleset framework — actor rules (users/roles/Apps/Copilot/Dependabot) and event rules (push/pull_request/pull_request_target/workflow_dispatch), with Evaluate mode (public preview 2026-06-18), **rule insights** with org-wide bypass metrics + CSV (public preview 2026-08-12), Actions Data Stream (preview), egress firewall (roadmap). https://github.blog/changelog/2026-06-18-control-who-and-what-triggers-github-actions-workflows/ ; https://github.blog/changelog/2026-08-12-rule-insights-for-organizations-in-public-preview/ ; https://github.blog/changelog/2026-07-14-dependabot-version-updates-introduce-default-package-cooldown/
- **The NHI (non-human identity) category consolidated in one summer**: Cisco→Astrix (~$400M, closed 2026-06-29), SailPoint→Entro (~$200M, closed 2026-06-29), Cyera→Oasis (~$1B LOI, 2026-07-28), Palo Alto→Koi (~$400M, 2026-02), Google→Wiz (closed 2026-03-11). The vendors who modelled GitHub Apps/PATs best are now inside identity/data-security conglomerates. https://blogs.cisco.com/news/cisco-announces-intent-to-acquire-astrix-security ; https://investor.sailpoint.com/news-releases/news-release-details/sailpoint-completes-acquisition-entro-security-secure-agentic ; https://techcrunch.com/2026/07/28/cyera-agrees-to-acquire-oasis-security-for-1b-to-safeguard-proliferating-ai-agents/ ; https://techcrunch.com/2026/03/11/google-completes-32b-acquisition-of-wiz/
- **The main architectural fork is runtime-agent vs API-read.** StepSecurity (Harden-Runner) and Cycode (Cimon) require a step/agent on the runner; everyone else reads the API. A third posture — *substitution* (Chainguard Actions, StepSecurity Maintained Actions) — replaces risky actions rather than observing them.
- **Nobody found does the full org-level object graph** (rulesets + environments + OIDC subject claims + fine-grained PATs + App installations + runner groups + workflows/pins) read-only in one model. Wiz is closest on paper; NHI vendors own the Apps/PATs slice; CI-posture vendors own the workflow-YAML slice. **Rulesets-as-objects and environments-as-objects: not found in any vendor's docs.**

### 1.1 StepSecurity — Harden-Runner + Actions Security Platform
- **Does**: runtime agent (Harden-Runner) on the runner — egress monitoring/blocking at DNS/L7/L3-4, file-write and process monitoring, imposter-commit detection, GitHub-API-call → minimal-token-permission inference. Enterprise tier adds an org-wide **Actions inventory** with pinned-vs-mutable analysis, automated pinning and least-permission PRs, "Known Compromised Actions" pre-execution gate, allowed-actions policy, **secrets metadata** (name/created/updated → unrotated secrets), daily branch-protection checks, and a "GitHub Apps visibility" bullet (pricing page only — undocumented). GitHub App asks for `actions:read`, `secrets:read`, `organization_secrets:read`. https://docs.stepsecurity.io/github-actions/harden-runner ; https://github.com/marketplace/harden-runner-app
- **Pricing (public)**: Community free (public repos); Dev Machine Guard $8/device/mo; Enterprise **$16/contributing developer/mo**. https://www.stepsecurity.io/pricing
- **User sees**: findings/detections dashboard, per-run insights (network events, file writes, recommended egress policy), actions inventory table, Threat Center. No graph.
- **Learn from**: per-job network baseline → auto-generated egress allowlist; the research→advisory loop (they surfaced the actions-cool imposter commits 2026-05-19 and much of the Trivy chain). https://www.stepsecurity.io/blog/10-layers-deep-how-stepsecurity-stops-teampcps-trivy-supply-chain-attack-on-github-actions
- **Gap**: workflow/actions-centric; no rulesets, PATs, OIDC, environments in docs; runtime value requires inserting the action into every workflow; Windows/macOS partial. $3M seed (2024-05), no later round — small team. Also: GitHub's roadmap egress firewall attacks their core.

### 1.2 Legit Security

- **Pricing**: sales only.
- **User sees**: inventory + findings + "visual models" (marketing; docs site unreachable — SSL failure — so unverified).
- **Learn from**: publishing the check-set as OSS (SARIF-emitting) built trust and a funnel.
- **Gap**: CI/CD product page 404s; site pivoted to AI/"VibeGuard"; no Apps/PAT/OIDC modelling evidenced; OSS tool wants broad admin classic PAT. No funding since $40M B (2023-09).

## 2. Open source projects — what they model, adoption, license, and CONSUME / REFERENCE / IGNORE

Verdict key: **CONSUME** = run it or call it and ingest output as findings/attributes on the grid. **REFERENCE** = port its checks/schema onto our own graph. **IGNORE** = off the critical path. Star counts and dates from `api.github.com/repos/*` on 2026-08-26 unless noted.

### 2.0 Headline findings

1. **Direct graph prior art exists and is recent.** SpecterOps' **BloodHound GitHub OpenGraph extension** (collector "GitHound", created 2025-07-23; newer "OpenHound GitHub collector") models a GitHub org as **27 node kinds and 152 edge kinds** — orgs, users, teams, custom roles, repos, branches, branch-protection rules, workflows/jobs/steps, org/repo/env secrets & variables, PATs, App installations, SAML identities, secret-scanning alerts — with *computed* privilege edges (`GH_CanWriteBranch`, `GH_CanPwnRequest`, `GH_CanAssumeIdentity` for OIDC→cloud). Read-only by design. This is the schema to study first. **Cartography** (CNCF, 4,028★) has a Python GitHub module ingesting org/users/teams/repos/branch protection/rulesets/CODEOWNERS/workflows/actions/secrets metadata/PATs/Dependabot alerts/GHCR into Neo4j. Cycode's **RAVEN** (746★, last release 2024-05) and OVO's **GitOops** (archived 2023) are older Neo4j approaches; Praetorian's **Trajan** (2026-03) emits Neo4j-compatible node/edge JSON.
2. **Nobody does change-over-time.** Every graph tool above is a snapshot (Cartography has `lastupdated` + cleanup, not history). Scorecard's weekly BigQuery cron is the only longitudinal dataset, and only for ~1M public repos.
3. **Workflow static analysis is a solved commodity** — zizmor (6,394★, ~650 adopters, 41 audits), poutine (13 rules, org mode), CodeQL's Actions pack (26 queries, on by default in code-scanning default setup), octoscan, actionlint, Semgrep. Consume; do not re-implement.
4. **The attacker's checklist is codified** in gato-x / Trajan and in BloodHound's Tier-Zero rules.
5. **GUAC** is the canonical supply-chain *artifact* graph; it does not model the CI/CD control plane at all. Its ontology discipline (every assertion stamped `origin/collector/justification/knownSince`) is the thing to borrow.

### 2.2 OpenSSF Scorecard (depth)

Docs: https://github.com/ossf/scorecard/blob/main/docs/checks.md. 5,653★, Apache-2.0, v5.5.0 (2026-04-23); scorecard-action 411★.

- **Checks (18)** — the CI/CD-relevant ones: **Branch-Protection** (High; 5 tiers: T1 no force-push/deletion → T2 ≥1 reviewer, PR required, up-to-date, last-push approval → T3 status checks → T4 ≥2 reviewers + code-owner → T5 dismiss-stale + admin enforcement; degrades gracefully without admin token); **Token-Permissions** (High; top-level read-only + minimal job-level; penalises write on `contents, packages, actions, deployments, security-events, statuses, checks`); **Pinned-Dependencies** (Medium; Actions SHA, Dockerfile digest, lockfiles); **Dangerous-Workflow** (Critical; untrusted checkout under prt/workflow_run; script injection from untrusted contexts) — **reused as a library by Allstar** (`checks.CheckDangerousWorkflow`), a precedent for calling Scorecard as a library; **Webhooks** (Critical, experimental; secret set; needs Webhooks:read); **Signed-Releases** (last 30 releases for `.sig/.sigstore/.intoto.jsonl`; presence only); **SAST**, **CI-Tests**, **Maintained** (≥1 commit/week over 90d), plus Code-Review, Contributors, Binary-Artifacts, Security-Policy, Vulnerabilities (OSV), Packaging, License, Fuzzing, CII-Best-Practices, Dependency-Update-Tool, SBOM.
- **Collection**: Go client mixing GraphQL (commits/PRs/reviews/issues), REST (branches, checkruns, releases, webhooks, workflows) and tarball download. Auth: classic `public_repo`, or GitHub App for rate limits; fine-grained PAT for Branch-Protection needs **Administration:read** (+ Webhooks:read optional); **repository rules readable with default `GITHUB_TOKEN`**. https://github.com/ossf/scorecard-action/blob/main/docs/authentication/fine-grained-auth-token.md
- **Public surfaces**: `https://api.scorecard.dev/projects/github.com/{owner}/{repo}` → `{date, repo{name,commit}, scorecard{version,commit}, score, checks[]{name,score,reason,details,documentation}}` (live check on ossf/scorecard: v5.5.0, 9/10, dated 2026-08-22); weekly cron over ~1M repos → BigQuery `openssf:scorecardcron.scorecard-v2` (CDLA-Permissive-2.0); deps.dev `GetProject` embeds Scorecard.
- **Verdict: CONSUME three ways** — (1) ingest the public API/BigQuery for every public action/dependency the org consumes (prior scoring of *upstreams*); (2) run Scorecard with our read-only token on the org's own repos and land each check as a timestamped finding; (3) import specific check functions as a library (Allstar precedent). It has no org-level graph and no per-org history — ours to add.

### 2.3 GUAC (depth) — the supply-chain artifact graph

OpenSSF incubating; created by Kusari, Google, Purdue; v1.0 June 2025, **v1.1.0 2026-03-13**; 1,534★, Apache-2.0. https://github.com/guacsec/guac ; ontology https://docs.guac.sh/guac-ontology-definition/

- **Model — three trees.** *Software tree (nouns)*: **Package** as a pURL trie (Package→Namespace→Name→Version→Qualifier), **Source** trie (tag xor commit), **Artifact** (algorithm+digest), **Builder** (URI, e.g. GitHub Actions), **Vulnerability** (OSV/GHSA/CVE), **License**. *Evidence tree (verbs, each carrying `justification / origin / collector / knownSince`)*: **IsDependency**, **IsOccurrence**, **HasSLSA** (artifact←builder+materials), **HasSBOM**, **HasSourceAt**, **CertifyScorecard** (GUAC already ingests Scorecard), **CertifyVuln**, **CertifyVEXStatement**, **CertifyBad/Good**, **CertifyLegal**, **HashEqual/PkgEqual/VulnEqual**, **PointOfContact/HasMetadata**. *Actor tree* (trust) is future work. 28 schema files.
- **Ingestion.** Collectors `blob, deps_dev, file, gcs, git, github (SBOM/provenance from releases + Actions run artifacts), kubescape, oci, s3`; certifiers `osv, scorecard, clearlydefined, eol, datadog_malware, attestation`; formats SPDX, CycloneDX, CSAF/OpenVEX, SLSA/in-toto ITE-6, DSSE. Backends keyvalue and ent/PostgreSQL complete; GraphQL server + REST.
- **Assessment.** GUAC models *artifacts and their provenance*, **not the CI/CD control plane** — no orgs, users, roles, workflows, permissions, runners, webhooks. It answers "what is in this build and is it vulnerable/signed"; git-serious answers "who can compromise this org's pipelines and how did that change." They meet at the **Builder** node. Two borrowings: (1) the evidence-tree discipline — every assertion stamped with source and time — is a direct template for git-serious provenance on the grid (TAP already has provenance/history as core grid concepts; GUAC is confirmation that the field has converged on the same shape); (2) if git-serious ever ingests SBOM/SLSA/Scorecard, feed GUAC rather than reimplement.
- **Verdict: REFERENCE (ontology/provenance modelling) + optional downstream CONSUME.** Complementary, not a competitor.

## 3. Best practices from name-brand sources — distilled to observable conditions

This section is the one a regulator leans on hardest. Each source is summarised for what it *actually* prescribes (not what vendors say it prescribes), then §3.10 collapses everything into a checklist of observable conditions tagged with the recommending source and the GitHub API surface that exposes it — or "not observable with a read-only credential."

### 3.1 GitHub's own canon: the "Secure use reference" (formerly "Security hardening for GitHub Actions")

Source: https://docs.github.com/en/actions/reference/security/secure-use (the enterprise-cloud mirror is identical). This is the single most-cited document in the field and the one every vendor checklist descends from. Its recommendations, grouped as GitHub groups them:

- **Secrets**: least-privilege credentials in workflows; never structured blobs (JSON/XML/YAML) as a secret; register derived secrets; audit how actions handle secrets; "Periodically review the registered secrets to confirm they are still required"; rotate; gate environment secrets with required reviewers.
- **GITHUB_TOKEN**: default permissions read-only for contents; grant extra permissions only per job.
- **Script injection**: prefer a JavaScript action over inline scripts; pass untrusted context (`github.event.*` titles, bodies, branch names) through intermediate env vars, never interpolate `${{ }}` into `run:`; enable CodeQL's workflow queries.
- **Untrusted checkout**: avoid `pull_request_target` and `workflow_run` unless necessary; "never checkout untrusted code when using these privileged triggers"; treat artifacts from other workflows as untrusted.
- **Third-party actions**: pin to a full-length commit SHA ("Pinning to a particular SHA helps mitigate the risk"); verify the SHA is from the canonical repo, not a fork; only tag-pin if you trust the creator ("Verified creator" badge); audit action source; apply the same to reusable workflows; enforce SHA-pinning via org policy.
- **Platform features**: put `.github/workflows` under CODEOWNERS; use OIDC instead of long-lived cloud secrets; Dependabot version updates for actions (note the caveat: "Dependabot only creates alerts for vulnerable actions that use semantic versioning" — SHA-pinned actions do NOT get alerts); disable Actions creating/approving PRs; code scanning; OpenSSF Scorecard.
- **Self-hosted runners**: "should almost never be used for public repositories"; not ephemeral by default; even private repos are exposed because "users with read access can fork and open pull requests"; use runner groups to limit blast radius; keep no long-lived creds on the runner; restrict metadata-service access; prefer JIT/ephemeral runners.
- **Audit**: monitor the org audit log; the example event is `org.update_actions_secret`.
- **Dependency graph**: the graph enumerates actions used per workflow with owner + pinned ref, "automatically sorted by vulnerability severity."

What GitHub's list does NOT say (gaps a world-class reviewer would notice): nothing about GitHub App installation permissions, nothing about PAT inventory, nothing about OAuth apps, nothing about ruleset bypass actors, nothing about cache poisoning, nothing about `persist-credentials`. Those come from the research community (§3.8).

### 3.3 OpenSSF — "Mitigating Attack Vectors in GitHub Workflows" (2024-08-12)

Source: https://openssf.org/blog/2024/08/12/mitigating-attack-vectors-in-github-workflows/. Four-point core: (1) minimum GITHUB_TOKEN permissions "reduces the damage any attack vectors could cause"; (2) never run untrusted code in privileged workflows or on the default branch — split into privileged/non-privileged workflows; (3) check actions for known vulnerabilities, prefer GitHub-owned actions; (4) use Scorecard to detect. Their framing that restricting permissions "doesn't make a compromised workflow completely harmless" is the correct posture — permissions are a blast-radius control, not a prevention.

OpenSSF's March 2026 advisory (Christopher Robinson, 2026-03-01; oss-sec 2026-03-03) on the autonomous "hackerbot-claw" campaign is the sharpest recent statement of *which* weak configurations are being exploited at scale: `pull_request_target`, untrusted fork code execution, inline shell with unvalidated inputs, branch/filename injection, missing authorization checks. Mitigations verbatim: "Avoid pull_request_target triggers where possible; prefer pull_request"; "Limit workflow permissions to the minimum necessary"; pin by commit hash; rotate secrets; enable audit logging. https://seclists.org/oss-sec/2026/q1/246

### 3.4 SLSA v1.2 (Nov 2025) — Build track and the new Source track

Sources: https://slsa.dev/blog/2025/11/announce-slsa-v1.2 ; https://slsa.dev/spec/v1.2/source-requirements ; earlier levels https://github.com/slsa-framework/slsa/blob/main/docs/spec/v1.0-rc1/levels.md. v1.1 approved April 2025, v1.2 released Nov 2025 (backwards compatible).

**Build track for a GitHub org**: L1 = provenance exists (builder identity, source, digest); L2 = hosted build platform generates + signs provenance (GitHub artifact attestations get you here out of the box); L3 = build platform hardened — ephemeral, isolated, signing material unreachable by user-defined steps (GitHub-hosted runners + `slsa-github-generator` reusable workflow or attestation with trusted builder). Observable proxy: does the release workflow call `actions/attest-build-provenance` / `slsa-framework/slsa-github-generator`, on GitHub-hosted (not self-hosted) runners, and do releases carry attestations (`GET /repos/{o}/{r}/attestations/{digest}`)?

**Source track** (new in 1.2) is the one that maps directly onto org configuration:
- **Source L1**: version control.
- **Source L2**: "Branch history is continuous, immutable, and retained"; SCS "record[s] all changes to Named References, including when they occurred, who made them"; Source VSAs per revision. GitHub mapping: branch protection/rulesets with **no force-push, no deletion**, tag protection.
- **Source L3**: "Enforce organizational technical controls" on protected named references, recorded in contemporaneously produced attestations, with tracked continuity from a start revision.
- **Source L4**: "Changes in protected branches MUST be agreed to by two or more trusted persons prior to submission"; uploader≠reviewer or two reviewers; "Informed Review"; exceptions only for documented Trusted Robots.

This is important prior art for the product: SLSA Source L2–L4 *is* a ruleset-posture model with a continuity requirement — "since which commit has this control been continuously enforced?" — which is exactly the change-over-time question a graph with history answers and a point-in-time scanner cannot.

### 3.5 CISA / NSA "Defending CI/CD Environments" (2023-06-28)

Sources: https://www.cisa.gov/news-events/alerts/2023/06/28/cisa-and-nsa-release-joint-guidance-defending-continuous-integrationcontinuous-delivery-cicd ; PDF https://media.defense.gov/2023/Jun/28/2003249466/-1/-1/0/CSI_DEFENDING_CI_CD_ENVIRONMENTS.PDF (403 to our fetcher; content taken from https://www.resilientcyber.io/p/defending-cicd-environments-the-nsacisa and https://www.chainguard.dev/unchained/strengthening-ci-cd-environments-insights-from-nsa-and-dhs-cisa-guidance). Three threat scenarios: compromised developer credentials; compromised libraries/tools/images; malicious modification of CI/CD or IaC configuration. Mitigations by category — *Authentication & access*: NSA-recommended cryptography; "Minimize the use of long-term credentials"; "Add signature to CI/CD configuration and verify it"; two-person rules for all code updates; least privilege; secure user accounts (MFA); secure secrets; network segmentation. *Dev environment*: patch OS/tools; remove unnecessary apps; EDR. *Process*: scanning in pipeline; restrict untrusted libraries/tools; analyze committed code; remove temporary resources; keep audit logs; SBOM/SCA; resiliency. It explicitly points at SLSA, CNCF supply-chain best practices, and the CIS Software Supply Chain Security Guide as the frameworks to adopt. It is a government-grade list, not GitHub-specific; its value to git-serious is as a citation for "long-lived credentials", "two-person rule", and "audit logs" observables.

### 3.6 NIST SP 800-218 SSDF v1.1 — the relevant tasks (exact text)

Source: https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf (Table 1, pp. 5–18). The tasks that a GitHub-org observer can evidence:

- **PO.3.1** "Specify which tools or tool types must or should be included in each toolchain to mitigate identified risks, as well as how the toolchain components are to be integrated with each other." → an *allowed actions* policy is the GitHub-native form of this.
- **PO.3.2** "Follow recommended security practices to deploy, operate, and maintain tools and toolchains." Examples include "Use code-based configuration for toolchains (e.g., pipelines-as-code)", "Continuously monitor tools and tool logs for potential operational and security issues", "Regularly verify the integrity and check the provenance of each tool."
- **PO.3.3** "Configure tools to generate artifacts of their support of secure software development practices" — audit trail.
- **PO.5.1** "Separate and protect each environment involved in software development." Examples: MFA + conditional access; "Minimize direct human access to toolchain systems, such as build services. Continuously monitor and audit all access attempts and all use of privileged access"; "Regularly log, monitor, and audit trust relationships for authorization and access between the environments."
- **PO.5.2** "Secure and harden development endpoints ... using a risk-based approach."
- **PS.1.1** "Store all forms of code – including source code, executable code, and configuration-as-code – based on the principle of least privilege so that only authorized personnel, tools, services, etc. have access." Examples: "Use version control features of the repository to track all changes made to the code with accountability to the individual account"; "Use commit signing"; "Have the code owner review and approve all changes made to the code by others."
- **PS.2.1** "Make software integrity verification information available to software acquirers." (hashes, code signing)
- **PS.3.1** "Securely archive the necessary files and supporting data (e.g., integrity verification information, provenance data) to be retained for each software release." **PS.3.2** "Collect, safeguard, maintain, and share provenance data for all components of each software release (e.g., in a software bill of materials [SBOM])."
- **PW.4.1** "Acquire and maintain well-secured software components ... from commercial, open-source, and other third-party developers" — Example 3: "Obtain provenance information (e.g., SBOM ...) for each software component, and analyze that information". **PW.4.4** "Verify that acquired ... third-party software components comply with the requirements" — Example 4: "Ensure that each software component is still actively maintained and has not reached end of life" (→ archived/unmaintained actions), Example 6: "Confirm the integrity of software components through digital signatures."
- **PW.6.1/6.2**: build tools "Perform all builds in a dedicated, highly controlled build environment" (Example 3 of PW.6.2).

SSDF is the compliance hook (EO 14028 attestation forms cite it); a git-serious "SSDF evidence" view that maps observed org state to PO.3/PO.5/PS.1/PS.3/PW.4 tasks is a plausible early-adopter pull for regulated teams — but note PO/PS tasks are organisational, so evidence is partial by construction.

### 3.7 OWASP Top 10 CI/CD Security Risks — each mapped to what git-serious could observe

Sources: https://owasp.org/www-project-top-10-ci-cd-security-risks/ and per-risk pages (CICD-SEC-01 … -10 under that path); cheat sheet https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html. Written by Cider Security (later Palo Alto) in 2022; still the canonical taxonomy. Quoted recommendations → observables:

| Risk | OWASP recommendation (verbatim where load-bearing) | git-serious observable |
|---|---|---|
| **SEC-1 Insufficient Flow Control** | "Configure branch protection rules on branches hosting code which is used in production ... avoid exclusion of user accounts or branches from branch protection rules"; "Limit the usage of auto-merge rules"; "prevent accounts from triggering production build and deployment pipelines without additional approval" | Rulesets/branch protection per default + release branches; **bypass actors** (see §3.10 caveat); auto-merge enabled; `workflow_dispatch` on deploy workflows without environment reviewers; who can push to protected refs |
| **SEC-2 Inadequate IAM** | "Conduct a continuous analysis and mapping of all identities across all systems ... For each identity, map the identity provider, level of permissions granted and level of permissions actually used. Ensure all methods of programmatic access are covered"; remove stale identities; expiry for external collaborators; no shared accounts | Members, outside collaborators, teams → repo permission edges; GitHub Apps + installations (permissions, repo selection); fine-grained PATs (`token_last_used_at`, `token_expires_at`); deploy keys (`read_only`, `last_used`); 2FA requirement; bot accounts with write |
| **SEC-3 Dependency Chain Abuse** | pull through internal proxy; "Enable checksum verification and signature verification"; "Avoid configuring clients to pull the latest version"; lockfiles; scopes; separate context for install scripts | Actions pinned by SHA vs tag vs branch; lockfiles present; Dependabot/Renovate config present; (npm/PyPI-side controls not observable from GitHub) |
| **SEC-4 Poisoned Pipeline Execution** | "pipelines running unreviewed code are executed on isolated nodes, not exposed to secrets"; "each branch that is configured to trigger a pipeline ... has a correlating branch protection rule"; review CI config before run; least repo permissions | Trigger × checkout-ref × permissions × secrets per workflow (the pwn-request signature); fork-PR approval policy (`fork-pr-contributor-approval`, `fork-pr-workflows-private-repos`); self-hosted runner on public repo; CODEOWNERS covering `.github/workflows`; runs whose `head_repository` is a fork |
| **SEC-5 Insufficient PBAC** | no shared nodes across sensitivity; secrets "scoped in a manner that allows each pipeline and step to have access to only the secrets it requires"; revert node to pristine state; network segmentation | Org secrets with `visibility: all` vs selected; environment secrets vs repo secrets; runner `ephemeral: false`; runner groups' repo access + `allows_public_repositories`; `secrets: inherit` in reusable-workflow calls |
| **SEC-6 Credential Hygiene** | "continuously map credentials found across the different systems"; temporary over static; rotation and stale detection; scope to conditions; detect secrets in repos; no printing to console; strip from artifacts | Secret inventory with `created_at`/`updated_at` age; OIDC use (`id-token: write`) vs cloud-key-named secrets (`AWS_SECRET_ACCESS_KEY`, `NPM_TOKEN`, `PYPI_API_TOKEN`); secret-scanning alerts; artifacts containing `.git` (ArtiPACKED) |
| **SEC-7 Insecure System Configuration** | "Maintain an inventory of systems and versions in use ... mapping of a designated owner"; least network access; "periodically review all system configurations for any setting that can have an effect on the security posture" | Org settings snapshot (2FA required, default repo permission, member repo-creation, Actions policy, default workflow permissions, `can_approve_pull_request_reviews`, retention); runner `version`; drift over time |
| **SEC-8 Ungoverned 3rd-Party Services** | vetting; "continuous visibility over all 3rd parties integrated to CI/CD systems, including: Method of integration ... Level of permission granted ... Level of permission actually in use"; deprovision unused | GitHub App installations (permissions, events, repo selection, suspended); org + repo webhooks (URL host, events, `insecure_ssl`, secret set?); PATs; **OAuth apps — no API** (gap); marketplace actions consumed (the action is itself a third party) |
| **SEC-9 Artifact Integrity** | sign resources, "validating against signing authorities"; commit signing; in-toto/SLSA/Sigstore; drift detection; verify third-party hashes | Ruleset "require signed commits"; attestations on releases; immutable-release enforcement; publish workflows using attest/provenance; `web_commit_signoff_required` |
| **SEC-10 Logging & Visibility** | "Mapping the environment — Develop a comprehensive inventory of all CI/CD systems"; enable audit + application logs; centralise; alert on anomalies | The inventory *is* the product; audit-log ingestion (GHEC-only via API — see §3.10); workflow-run stream (`triggering_actor`, `event`, `head_repository`) as the application log |

Notable: SEC-10's first recommendation is literally "Mapping the environment." A read-only graph of the org is the OWASP-sanctioned starting point, which is a useful sentence for early-adopter conversations.

### 3.8 Research-community findings (2023–2026) — the attack patterns and the numbers

- **Legit Security, "State of GitHub Actions Security" (2024-07)**: untrusted-input interpolation in >7,000 workflows; untrusted code execution in >2,500; untrustworthy artifacts in >3,000; of 19,113 marketplace actions only 913 by verified creators, 18% with vulnerable dependencies, 762 archived. Also their `workflow_run` privilege-escalation write-up. https://www.legitsecurity.com/press-releases/the-state-of-github-actions-security ; https://www.legitsecurity.com/blog/github-privilege-escalation-vulnerability
- **Unit 42 "ArtiPACKED" (2024-08)**: `actions/checkout` persists the token in `.git/config`; uploading the checkout dir as an artifact leaks `GITHUB_TOKEN` (`ghs_`) and `ACTIONS_RUNTIME_TOKEN`; 14 large projects (Google, Microsoft, AWS, Red Hat) affected. Observable: artifact contains `.git/config`; `persist-credentials` not set to false. https://unit42.paloaltonetworks.com/github-repo-artifacts-leak-tokens/
- **Adnan Khan, "The Monsters in Your Build Cache" (2024-05)**: with code exec in any default-branch-scoped workflow, an attacker obtains `CacheServerUrl`/`AccessToken` and poisons cache entries later restored by privileged workflows — "tamper with a SLSA Level 3 build artifact ... without leaving a trace." Cited as a component of the May 2026 TanStack compromise. Observable: cache use (`actions/cache`, `setup-*` with cache) in a workflow that runs with secrets *and* any lower-trust workflow on the same repo/default branch. https://adnanthekhan.com/2024/05/06/the-monsters-in-your-build-cache-github-actions-cache-poisoning/ ; CodeQL query: https://codeql.github.com/codeql-query-help/actions/actions-cache-poisoning-code-injection/
- **Adnan Khan / John Stawinski — self-hosted runner campaign (2023-12 → 2024-01)**: PyTorch, TensorFlow, Microsoft DeepSpeed, GitHub's own runner-images; non-ephemeral self-hosted runners on public repos + "first-time contributor" approval bypass by getting a trivial PR merged. https://adnanthekhan.com/2023/12/20/one-supply-chain-attack-to-rule-them-all/ ; https://johnstawinski.com/2024/01/11/playing-with-fire-how-we-executed-a-critical-supply-chain-attack-on-pytorch/ ; https://www.praetorian.com/blog/tensorflow-supply-chain-compromise-via-self-hosted-runner-attack/
- **Synacktiv, self-hosted runners (2024-07-17)**: attacker discovery via `runs-on` labels, run logs ("Cleaning the repository" = shared workdir; identical runner names across jobs = non-ephemeral); `.git/config` token of the *triggering user*; "exclusively employ them with private repositories". https://www.synacktiv.com/en/publications/github-actions-exploitation-self-hosted-runners
- **Orca "pull_request_nightmare" Part 2 (2025-09-30)**: Fortune-100 RCE (Microsoft/symphony CVE-2025-61671 CVSS 9.3; Google/ai-ml-recipes; Nvidia/nvrc → self-hosted runner + AWS IMDS). Pattern: `pull_request_target` + checkout of `refs/pull/N/merge` / `head.sha` / `head_ref` + `contents: write`/`packages: write`. Mitigation: `if: github.event.pull_request.head.repo.full_name == github.repository`, label gating, environments with reviewers. "thousands of vulnerable repositories" among 100,000+ using `pull_request_target`. https://orca.security/resources/blog/pull-request-nightmare-part-2-exploits/
- **Unit 42 "OH-MY-DC" OIDC misconfigurations (2025-04-04)**: loose federation policies (validating always-true claims); trusting user-controllable claims (branch names, workflow filenames); custom-sub ordering attacks; CircleCI handing fork workflows the target's OIDC identity. https://unit42.paloaltonetworks.com/oidc-misconfigurations-in-ci-cd/ — plus Datadog https://securitylabs.datadoghq.com/articles/exploring-github-to-aws-keyless-authentication-flaws/ and Wiz https://www.wiz.io/blog/avoiding-mistakes-with-aws-oidc-integration-conditions on missing `sub` conditions and `repo:org/*` wildcards. **Critical limit**: the cloud-side trust policy is invisible from GitHub; only the GitHub side (sub-claim customization, `id-token: write`, which workflows/envs request tokens) is observable.
- **Wiz, "Hardening GitHub Actions: Lessons from Recent Attacks" (updated 2026-04-15)**: cites tj-actions (2025-03), trivy-action/TeamPCP (2026-03), Axios (2026-03). Adds: `permissions: {}` at workflow level; never `toJson(secrets)`; avoid `secrets: inherit`; `persist-credentials: false`; "7-14 day delay before adopting new action versions catches 80-90% of supply chain attacks" (cooldowns); prefer GitHub Apps over workflow secrets; egress deny-by-default on self-hosted. "the window between compromise and detection is hours, not days." https://www.wiz.io/blog/github-actions-security-guide
- **Datadog Security Labs (2026-06-02)**: 38% of orgs have a workflow vulnerable to script injection or dangerous triggers; 2 of 3 orgs have at least one vulnerable workflow/action; **71% of orgs never pin actions to a commit hash**. https://securitylabs.datadoghq.com/articles/case-for-github-actions-security/ ; Datadog's 2026 DevSecOps study https://www.datadoghq.com/blog/devsecops-2026-study-learnings/
- **Andrew Nesbitt, PyPI ecosystem scan with zizmor 1.24.1 (2026-05-09..11, published 2026-05-25)**: 387k packages → 343k repos → ~152k with workflows; **~91% of repos using third-party actions have unpinned refs** (pypa/gh-action-pypi-publish 84% unpinned, codecov-action 92%); 21,166 repos with template-injection patterns (1,396 with attacker-controlled data); ~7,025 with `pull_request_target`/`workflow_run`; only ~22% of pypi-publish users on trusted publishing, ~44,000 still holding a `PYPI_API_TOKEN` secret. https://nesbitt.io/2026/05/25/github-actions-security-in-python-packages.html
- **Trail of Bits + zizmor corpus (2026-05-22)**: built a 41,253-workflow corpus from the 6,612 Actions-using repos among the 10k most-starred 2022–2025 repos (BigQuery GitHub dataset); found/fixed 45 zizmor crashes. Methodologically relevant: the BigQuery corpus is a reusable prior-art/benchmark technique. https://blog.trailofbits.com/2026/05/22/we-hardened-zizmors-github-actions-static-analyzer/
- **Chainguard Octo STS**: a GitHub App acting as an STS — exchange any OIDC token for a 1-hour, tightly-scoped GitHub token; "the end of GitHub PATs". Prior art for *how a well-run org replaces PATs*, and therefore for a "long-lived PAT where OIDC/App would do" finding. https://edu.chainguard.dev/open-source/octo-sts/overview/ ; https://www.chainguard.dev/unchained/the-end-of-github-pats-you-cant-leak-what-you-dont-have

- **GitHub Apps / NHI research**: no API lists OAuth apps with org access (community discussion #172047, confirmed gap); Astrix/Arnica research on thousands of third-party NHIs per large org; a 2022 GitHub bug escalated App read→write for a week. https://github.com/orgs/community/discussions/172047 ; https://astrix.security/learn/blog/insecure-third-party-connections-to-your-github-may-trigger-a-supply-chain-attack/ ; https://www.aquasec.com/blog/github-app-tokens/

The lesson is architectural: *attestations collected along the SDLC, enforced at deploy time*. GitHub's artifact attestations + immutable releases are the GitHub-native analogue. https://cloud.google.com/blog/products/devops-sre/introducing-software-delivery-shield-from-google-cloud ; https://security.googleblog.com/2021/06/introducing-slsa-end-to-end-framework.html
- **CIS**: there is a CIS Software Supply Chain Security Guide (referenced by CISA/NSA) and a CIS GitHub Benchmark v1.0.0 (branch-protection style controls: require PR, code-owner review, status checks); coverage of Actions is thin. https://www.scribd.com/document/656364334/CIS-GitHub-Benchmark-v1-0-0-PDF (unverified quality of that mirror; the canonical PDF is behind CIS registration).

Three consequences for the product's credential design (flagged, to be tested empirically against our own org before it becomes spec):

1. **A GitHub App installation, not a PAT, is the right "read-only credential."** Fine-grained PATs inherit the *user's* role, so "Administration: read" org endpoints only work for a PAT minted by an org owner; the PAT-inventory endpoints are *GitHub-App-only*; and Apps get an installation-scoped, auditable identity that appears as a third party in the very inventory we build (nice reflexivity: git-serious can show its own permissions).
2. **Ruleset bypass actors — the single most important SEC-1 fact — are hidden from read-only callers by design.** Either accept `Administration: write` on rulesets (which contradicts read-only), or infer bypass from rule-suite evaluation history, or ask the operator to grant write to that one permission with a documented reason. Needs a real test; do not assume.
3. **The audit log is a GHEC feature.** For Team-plan orgs (our own, friends, most early adopters) the "track change over time" promise must be *derived* by snapshot diffing — which is what a graph with history does anyway, and is arguably the more honest design (we observe the state, not the platform's story about the state).

### 3.10 The observable-conditions checklist

Format: **condition** — recommending sources — API surface (read-only reachable? ✅ / ⚠️ needs elevated / ❌ not observable). Ranked roughly by incident evidence (see §4) within each group.

**A. Workflow-level (from YAML + runs)**
1. **Action `uses:` pinned by full 40-hex SHA, not tag/branch** — GitHub secure-use; OpenSSF; Wiz; Datadog; Scorecard Pinned-Dependencies; zizmor `unpinned-uses` — Contents read ✅. Incident evidence: tj-actions (2025-03), reviewdog, trivy-action (2026-03), Ultralytics chain.

Two readings a regulator should take from the table. First, the top three rows are *conjunctions*: the deadly pattern is "mutable ref × privileged trigger × long-lived secret", and the 2026 incidents (TanStack, Trivy, LiteLLM) are explicitly chains of 2–3 preconditions that individually look tolerable. Change-over-time is where the observable signal moved in 2025–2026.

## 6. Implications for git-serious

Ranked by incident evidence (§4.1) and by what the read-only posture can actually observe (§3.9).

1. **Model the conjunction, not the setting.** The top three incident classes are `mutable-ref × privileged-trigger × long-lived-secret` chains (TanStack, Trivy→LiteLLM, Nx, tj-actions, Ultralytics, Kong, Angular). The graph must make "workflow W (trigger T, checkout ref R, permissions P) → uses action A@ref (mutable? owner? tag→SHA drift?) → reaches secret S (age, scope, name-class) / cache key K / OIDC token (environment E)" a single traversal. A Gryphon query that returns that path is the product's first killer finding; a list of three separate lints is not.
2. **Change-over-time is the differentiator, and it must be snapshot-derived.** Detections that would have caught 2025–26 incidents are deltas: every tag of a consumed action moved in one burst; a self-hosted runner appeared on a repo that never had one; a workflow file authored by a first-time committer; a new outside collaborator; a secret updated while an older token stayed valid; a vulnerable workflow surviving on a non-default branch after removal from `main`. None of the graph tools (BloodHound-GitHub, Cartography, RAVEN, Trajan) keep history; the audit log is GHEC-only. TAP's grid already has history/provenance as core concepts — lean on it; make every collector run a versioned observation and ship "what changed since last observation" as the default view.
3. **Credential design: a GitHub App with read-only permissions, shown in its own inventory.** Facts: fine-grained PATs inherit the user's role (org Administration:read reads need an owner's PAT); PAT enumeration is App-only; installation tokens are short-lived (octo-sts pattern); an App appears as a third party in the SEC-8 inventory we build — git-serious should render its own permissions as the first row. Name the two things read-only cannot see (ruleset `bypass_actors` without write; OAuth apps at all) in the UI rather than implying completeness (security-posture doctrine: name the risks left open). Open question §5.1 gates the exact permission set.
4. **Node and edge types implied by the evidence** (minimum viable, in priority order): Organization (settings snapshot), Repository (visibility, default branch), Workflow → Job → Step (trigger set, `permissions`, `runs-on`, checkout ref, cache keys, `id-token`), ActionRef (owner/repo, ref kind SHA/tag/branch, resolved SHA at observation, canonical-repo check), Secret/Variable (scope org/repo/env, visibility, created/updated, name-class heuristic), Environment (reviewers, wait timer, branch policy, prevent-self-review), Ruleset/BranchProtection (rules, enforcement, targeting, bypass actors when visible), Runner + RunnerGroup (ephemeral, labels, public-repo access), AppInstallation (permission map, repo selection, events, suspended), FineGrainedPAT (owner, perms, expiry, last-used), DeployKey, Webhook (host, events, ssl, secret-set), Member/OutsideCollaborator/Team → repo permission edges, WorkflowRun (event, actor, triggering_actor, head_repository fork flag, referenced_workflows SHAs), Release/Attestation. Edges: `USES_ACTION`, `RESOLVES_TO_SHA`, `READS_SECRET`, `RESTORES_CACHE`/`WRITES_CACHE`, `DEPLOYS_TO_ENV`, `PROTECTED_BY`, `BYPASSES`, `INSTALLED_ON`, `CAN_WRITE` (computed, BloodHound-style), `TRIGGERED_BY`, `RUNS_ON`. Borrow names from BloodHound's schema and Cartography where they fit; the computed `GH_CanWriteBranch` merge-gate/push-gate logic is worth porting verbatim.
5. **Consume, don't rebuild: zizmor + poutine + Scorecard + CodeQL alerts + OSV.** Run zizmor (`json-v1`) and poutine (`analyze_org`) with our read-only token; land their finding IDs as typed findings attached to Workflow/Step nodes; pull Scorecard's public API/BigQuery for every *upstream* action the org consumes (Maintained, Signed-Releases, Dangerous-Workflow, Token-Permissions of the action's own repo) and run Scorecard on the org's own repos; ingest existing code-scanning (CodeQL Actions pack) and Dependabot `actions` alerts via API; query OSV's GitHub Actions ecosystem. Record `origin/collector/justification/knownSince` on each (GUAC's evidence discipline) so scanner disagreement is data, not confusion.
6. **Reference, don't consume: legitify + Moat + BloodHound queries + gato-x enumeration + OSPS Baseline.** These are the rule sets to port as Gryphon queries over our graph (they need admin-scoped classic PATs or a Neo4j). gato-x's enumeration list (self-hosted runner reachability, pwn-request candidates, injection sinks, TOCTOU, `if:` gate simulation) is the attack-surface checklist; never run its attack modes with a customer credential.
7. **The ranked observable list for v0** (from §3.10 and §4.1): (a) action refs by mutability + tag→SHA drift since last observation; (b) `pull_request_target`/`workflow_run`/`issue_comment`/`discussion` workflows with fork checkout or event-text interpolation, and their reachable secrets/OIDC/cache; (c) secret inventory with age, scope and name-class (cloud/registry tokens where OIDC exists); (d) default-branch protection: PR required, reviews, force-push/deletion, `enforce_admins`, CODEOWNERS on `.github/workflows`, signed commits — with bypass where visible; (e) org policy snapshot: `sha_pinning_required`, `allowed_actions`, `default_workflow_permissions`, `can_approve_pull_request_reviews`, fork-PR approval policy, 2FA requirement, default repo permission; (f) self-hosted runners: ephemeral flag, public-repo exposure, runner-group scope, *appearance delta*; (g) App installations and fine-grained PATs: permission breadth, `repository_selection=all`, expiry, last-used, install date; (h) environments with reviewers/branch policy on publish/deploy workflows; (i) webhooks and deploy keys; (j) publish chain: trusted publishing vs token, attestations on releases, immutable-release enforcement; (k) membership/collaborator deltas.
8. **Where read-only + graph-first is genuinely differentiating**: change-over-time on org state; conjunction findings across object types; "granted vs used" for Apps/PATs (CICD-SEC-2/-8 verbatim); SLSA Source-track continuity ("enforced since revision X"); a self-describing collector whose own permissions are in the inventory; evaluate-mode style "what would change if I enforced X" computed from the graph (GitHub's own Evaluate mode is per-ruleset and forward-looking; ours can be retrospective across the org).
9. **Where it is table stakes** (must exist, will not win): per-workflow lint findings (zizmor/CodeQL do it better), pin drift PRs (Dependabot/Renovate/pinact), branch-protection tiers (Scorecard), SHA-pinning status (one org field now), secret-in-code detection (GitHub secret scanning + kingfisher).
10. **Where GitHub will eat the lane within 12 months** (do not build): egress monitoring on hosted runners (roadmap firewall), workflow lockfiles (roadmap `dependencies:`), who-can-trigger rulesets (shipping), rule insights (shipping), audit streaming (Data Stream). Treat each as an *input* to the graph and design the collectors to ingest them when GA.
11. **Player-3 posture is table stakes, not stretch.** The attacker side already automates (hackerbot-claw, prt-scan, gato-x scanning 40k repos/hour, gato-x's MCP server). Ship the graph, the finding taxonomy and each collector's permission needs as machine-legible, described, queryable metadata from day one; the AI review surface reads the graph, never writes it (spec-ai-integration). Endor Labs shipping posture as Claude Code plugins is the commercial signal.
12. **Compliance hooks are cheap edges.** Tag each finding with the standards that recommend it (OWASP CICD-SEC-n, SLSA Source/Build level, SSDF task IDs, OSPS Baseline IDs, CISA/NSA) — the mapping in §3.7/§3.10 is already done; regulated early adopters (SSDF attestation forms, OpenSSF badge chasers) get a "why this matters" for free and a pull toward trials.
13. **Read-only must include artifact and log reads.** ArtiPACKED-class findings require downloading artifacts; runner-ephemerality heuristics require job logs; both are `Actions: read`. Budget rate limits and storage for them; do not treat "read-only" as "metadata-only."
14. **Second collectors, in order of incident evidence**: cloud-side OIDC trust policies (AWS IAM first — reuses aws-core), then package registries (npm/PyPI provenance and publisher config), then GitLab. Each closes an "[not observable from GitHub]" row in §3.10.
15. **Our own org is the first test case for every open question in §5.** Install the read-only App, run OpenHound/gato-x-enumerate/zizmor/poutine/Scorecard against `unified-systems-com`, diff their outputs against our model, and record what each credential level could and could not see. That record becomes both the collector spec and the first "prior-art research" skill artifact.

### 7.4 Proposed shape for a reusable "prior-art research" skill

**Inputs**: (1) a product one-liner + problem line; (2) the object-of-study list (what the product observes/does); (3) a seed list of named competitors/tools/incidents (the caller's priors — to be *tested*, not trusted); (4) the target audience's posture constraints (e.g. "read-only credential", "no agent on runner"); (5) date, and a recency bias rule ("prefer last 18 months; note dates on everything").

**Steps**:
1. *Frame the observable question first.* Before searching, write the list of conditions the product could in principle observe; every source is then read for "what does this recommend/exploit that maps to an observable?" This is what made §3.10 and §4.1 possible.
2. *Fan out by stream, not by source type*: commercial products; open source; canonical guidance/standards; incidents; platform API surface. Each stream gets its own agent with an explicit "richest vs thin" reporting duty and a "queries run" log. Send mid-course corrections when one stream's findings (e.g., a fresh incident) should redirect another.
3. *Capability claims only from docs, pricing, changelogs, or code*; marketing pages produce a "claimed" row, never a "does" row. For OSS, hit `api.github.com/repos/<o>/<r>` for stars/license/pushed_at and `/releases/latest` for cadence.
4. *Platform-surface pass*: for every observable, find the exact endpoint, the fine-grained permission and level, and the returned fields; mark ✅ / ⚠️ elevated / ❌ not observable. This is the highest-value, least-glamorous step and should be a standing table maintained in the spec.
5. *Incident ledger with precondition extraction*: for each incident record date, vector chain, root cause, blast radius, observable precondition, one-line detection, primary source; then build the precondition frequency table. Rank the product's observables by that table, not by intuition.
6. *Verdict table for OSS*: CONSUME / REFERENCE / IGNORE with a one-line reason; make CONSUME the default for mature analyzers and REFERENCE for rule sets that need elevated credentials.
7. *Honest-gaps section*: list what could not be verified, with the next test (preferably empirical on our own org) or the person to ask.
8. *Budget discipline*: reserve ~15% of the search budget for the end-of-pass confirmation sweep; this pass did not and lost it.

**Outputs**: one markdown report in the seven-section shape used here (products; OSS; best practices → observable checklist; incidents → precondition frequency; unknowns; implications; method log), with URLs on every load-bearing claim, dated, and with a 12-line executive summary — plus, as a side artifact, the *observable ↔ API-surface* table and the *incident ↔ precondition* table as machine-readable JSON/YAML so the product's collectors and finding taxonomy can cite them (Player-3 legibility). Depth over breadth in best practices, incidents and implications; breadth is enough for products.
